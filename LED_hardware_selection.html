Hardware selection guide

200-LED audio-reactive spiral

This guide uses SousaVFX.ino, coordinate_maps.h, and palettes.h as the starting point for choosing hardware. It is a selection and validation guide, not a drop-in port: the existing sketch is written for a Teensy 3.2 and OctoWS2811.

Short recommendation

Prototype with an ESP32-S3 development board, an I2S digital MEMS microphone, and 5 V WS2812B-compatible pixels, arranged as eight independently driven 25-pixel strands. Use the ESP32-S3's I2S peripheral for the microphone and a tested parallel LED backend (for example, FastLED's ESP32 parallel-I2S backend) for the eight LED data lanes. Confirm that the exact board/core/library combination permits both peripherals simultaneously before buying final wiring or committing to a board revision.

An Adafruit Feather RP2040 SCORPIO is an attractive alternative if built-in eight-lane WS2812 output is the top priority: its PIO-based NeoPXL8 driver supports eight outputs concurrently, and has a 3.3-to-5 V level shifter. But RP2040 has no dedicated I2S peripheral, so I2S microphone input uses a PIO/software implementation and may compete with the LED driver's PIO resources. Test that combination early; the ESP32-S3 is the simpler choice when I2S audio is a firm requirement.

What the reference code tells us

  • The current source defines 8 strips × 26 pixels = 208 LEDs (ledsPerStrip, numStrips, and NUM_LEDS). Its own comments say the map was meant for eight rows of 25, with an extra pixel added. The new installation is 8 × 25 = 200 LEDs. Update the dimensions consistently and regenerate or carefully remap the coordinate tables for the new physical curves; do not just change a loop bound and leave 208-entry mappings in use.
  • Each rendered frame loops over all 208 LEDs, doing floating-point phase/radius work, lookup-table easing and integer color scaling. The high-resolution map includes several arrays of float; the LED colors themselves occupy only 3 bytes per pixel (about 600 bytes for 200 LEDs). The coordinate tables and driver buffers add more RAM, but 200 pixels is a small buffer for modern boards.
  • The sketch's 260 FPS interval is about 3.85 ms. At 60 FPS, one frame is available every 16.67 ms, and there are only about 12,000 pixel iterations per second (200 × 60), versus about 54,000 for 208 × 260. Reducing the target frame rate therefore cuts this loop workload by over four times. There is no reason to select a high-end processor for this pixel count; reliable LED timing, enough GPIO/peripheral resources, microphone support, and power delivery matter more.
  • This is an estimate from source structure, not a benchmark: actual frame time depends on compiler, LED library, audio processing, and other tasks. Measure render time on the chosen board and target a comfortable margin under 16.67 ms.
  • The reference code does not currently read a microphone or calculate audio amplitude; the I2S capture and amplitude/envelope logic will be new code.
  • Rendering is currently gated by newData, which is set by the serial parameter receiver. For a standalone audio-reactive build, schedule rendering from a 60 FPS timer (or equivalent) independently of serial input, and update the animation parameters from microphone samples.
  • MAX_POWER_MW is set to 40,000 mW (40 W) in the sketch. Treat that as a software brightness/power estimate, not as a current limiter or electrical protection device.
  • The existing OctoWS2811 output code is Teensy-specific. Keep the effect and palette logic where practical, but replace the LED transfer/output setup for the target board. Also check the LED mapping and the configured LED type/color order against the actual purchased pixels.

Choosing a microcontroller

Look for all of these:

  1. Enough compute headroom: a 32-bit MCU with a hardware LED peripheral or DMA support. The render math is modest at 60 FPS, but hardware-driven outputs avoid wasting CPU on exact WS2812 pulse timing.
  2. Eight outputs, or a viable way to provide them: each physical strand should be its own data lane if all eight are to update together. Check the board's available transmitter channels/backend limits, not only its total GPIO count. If outputs are grouped or serialized, confirm their combined transmit time still leaves room in the 16.67 ms frame.
  3. Digital I2S receive: confirm that the MCU has I2S input and that the selected library/framework can run it concurrently with LED output. DMA-based continuous sampling is preferable.
  4. Enough pins, memory, and software support: reserve the microphone clock/data pins and eight pixel pins (plus any controls), verify board voltage levels, and confirm FastLED or an equivalent driver supports the board and chosen LED type.
  5. Actual total cost and availability: compare the assembled development board and required level shifters, driver hardware, regulator, and charger—not just the bare chip price.

Selecting the LEDs and output arrangement

  • For least code change, start with 5 V WS2812B-compatible RGB pixels/strips. FastLED already handles the palette/rendering style, and this retains a one-wire data lane per strand. Buy from a seller that provides a datasheet and identifies the actual controller and color order; generic “WS2812-compatible” parts can differ in timing and voltage behavior.
  • Use eight separate 25-pixel strands, each with its own data output, arranged along the eight curves. Connect their grounds to the controller ground. Feed power in parallel; do not try to power all LEDs through the MCU board or connect the strips as a single physical chain unless the chosen mapping and output arrangement are designed for it.
  • For 800 kHz WS2812-style signaling, 25 pixels need about 0.75 ms of data time per lane (25 × 24 bits × 1.25 µs). Eight lanes sent in parallel take about that much data time; if sent one after another, the payload is about 6 ms before reset gaps. Both are nominally compatible with a 16.67 ms 60 FPS period, but include reset time, rendering, microphone work, and library behavior in the actual timing test.
  • Other addressable pixels can work, but check protocol and library support. SK6812 RGBW pixels use a different pixel format from RGB WS2812B. Clocked pixels such as APA102/SK9822 avoid strict one-wire timing but require clock and data wiring (potentially 16 signals for eight independent strands) and may use more pins. Choosing another LED family does not remove the need to size the power system.
  • Update the code to 200 LEDs / 25 per strand and remap the existing coordinate arrays to the actual curve layout. Each strand's LED order and start/end direction must match the indices used by the render code. Regenerate the map if the curves or pixel spacing differ.

Power and wiring budget for 5 V RGB pixels

Use the specific pixel datasheet and measure your built effect. As a conservative WS2812B-style planning figure, allow up to 60 mA per pixel at full-white maximum brightness:

  • 200 × 60 mA = 12 A at 5 V, or 60 W theoretical maximum.
  • The reference sketch has a 40 W software cap, equivalent to about 8 A at 5 V if that estimate matches the selected pixels. Use a regulated supply and wiring sized for the electrical worst case you intend to permit, not just for a software setting.
  • Adafruit's rough animation estimate is 20 mA per pixel: about 4 A / 20 W for 200 pixels. This is only a starting estimate; bright white and high brightness can raise the load considerably. Measure current with the real palettes, audio response, and configured brightness.

For a robust layout:

  • Use a regulated 5 V supply/buck converter with appropriate continuous-current rating and margin. If you enforce the 40 W design limit in software, a 5 V, 10 A class output is a reasonable starting point to evaluate; if the build must tolerate unrestricted full-white, size for at least 12 A plus margin (for example, a 15 A class system). Check the converter's thermal performance and real output rating.
  • Run suitably thick power and ground wiring to the strands, with power injection at the start of each strand and additional injection if voltage drop measurements require it. Fuse the battery/main feed and choose branch fuses based on wire ampacity and measured branch current.
  • Add a 500–1000 µF capacitor across the LED supply near its distribution point. Use a 300–500 Ω series resistor on each data line, near the first pixel, unless the pixel product already incorporates suitable protection.
  • A 3.3 V MCU output driving 5 V pixels should normally use a 5 V logic-level buffer (for example, an AHCT-family buffer). The SCORPIO includes shifting for its eight NeoPixel outputs; most ESP32-S3 boards do not. Keep signal wiring short and ensure common ground.
  • Power the LEDs from the dedicated 5 V rail, not from the MCU regulator or USB pin. Follow the LED manufacturer's sequencing and wiring recommendations.

Selecting an I2S microphone

Use a digital I2S MEMS microphone module that exposes the microphone data, bit clock (BCLK/SCK), and word-select/left-right clock (WS/LRCLK); some also need or support MCLK. Confirm voltage compatibility, pinout, I2S slot format, supply voltage, and the current lifecycle/availability of the exact part. Connect the mic to a dedicated I2S receive peripheral if available, keep its clock/data wiring short, and join grounds.

Do not pick a microphone solely because an old example uses it: TDK lists the ICS-43434 as end-of-life. INMP441 breakout modules are common, but verify that the specific module is genuine, available, and suitable for your supply and I2S format. Prefer an in-production microphone from a traceable supplier.

For ambient amplitude response, a full spectrum analyzer is unnecessary. A practical starting point is mono audio at 16 kHz, receive samples by I2S DMA, compute a short block's peak or RMS level, apply an envelope/attack-release smoother, then map the result to brightness, palette motion, or another animation parameter. At 16 kHz and 60 FPS, a frame corresponds to about 267 samples. Confirm how the selected driver places 24-bit mic data in 32-bit I2S slots and handle sign extension/scaling correctly. Keep audio capture running continuously; the LED frame loop should consume the most recent amplitude value without blocking for a whole audio buffer.

Rechargeable battery and runtime sizing

First decide the required runtime and measure average power at representative brightness and sound levels. Battery capacity in watt-hours is more useful than mAh when comparing different pack voltages:

battery energy (Wh) = nominal pack voltage (V) × capacity (Ah)
usable load energy (Wh) ≈ battery Wh × allowed usable fraction × converter efficiency
runtime (hours) ≈ usable load energy (Wh) ÷ average system load (W)

Use the pack manufacturer's rated capacity and discharge-current limit. Allow for cell aging, temperature, converter losses, and a reserve; do not calculate runtime from peak LED power unless you intentionally want a conservative worst-case estimate.

Illustrative example: a 2-cell series (2S) lithium-ion pack rated 7.4 V, 5 Ah contains about 37 Wh nominally. If 85% is treated as usable and the 5 V converter is 90% efficient, about 28 Wh reaches the load. That is approximately 1.4 hours at 20 W average, or 0.7 hours at 40 W average. Actual runtime will differ; measure it. A higher-voltage pack can reduce battery-side current for a given power, but requires a buck converter rated for the full 5 V LED current.

For a portable build, compare these practical options:

  1. A commercial protected battery pack (for example, a 2S or 3S Li-ion pack with protection/BMS) plus a correctly rated 5 V buck converter. Use a charger matched to the pack's series count and chemistry. This is often practical for a several-amp LED load.
  2. A single-cell Li-ion/LiPo pack plus 5 V boost converter only if the boost converter and battery can supply the high input current. At 40 W output, a 1S pack may need well over 10 A after conversion losses; many small boost boards and pouch cells cannot safely provide that.
  3. A USB power bank only if its 5 V port is explicitly rated for the required continuous current and it does not shut off at changing loads. Many ordinary power banks cannot supply the 8–12 A this design could need from a single 5 V output.

Use a reputable, protected pack with adequate continuous-discharge rating, a matching charger, a main fuse close to the battery, strain relief, and an enclosure that prevents puncture or shorting. Do not build a pack from loose lithium cells without the required cell-matching, protection, charging, and battery-pack expertise. Keep the high-current LED rail separate from the board's 3.3 V logic rail except for common ground.

A low-risk selection and test plan

  1. Buy one candidate MCU board, one I2S mic breakout, and a short/sample quantity of the intended pixel type. Confirm the supplier's exact pixel datasheet and strand current before ordering all 200 LEDs.
  2. Prove microphone input alone: stream I2S samples, inspect the signed sample range, and display or log a stable amplitude envelope in a quiet room and with sound.
  3. Prove eight-strand LED output separately using 25 pixels per lane, a conservative brightness limit, proper level shifting, and a current-limited bench supply. Verify all eight strands and color order. For ESP32-S3, test eight-lane parallel output with the mic I2S driver enabled at the same time; do not assume peripheral compatibility from chip specs alone.
  4. Port the coordinate mapping to 200 entries and the physical spiral. Keep the render loop at 60 FPS from a timer and process audio in short, non-blocking DMA buffers.
  5. Measure worst-case render time, missed frames/audio overruns, LED current, voltage at the far end of each strand, and converter temperature. Test bright white at the intended maximum brightness. Adjust wiring, injection, fuses, and converter rating before using the battery.
  6. Run the full pattern and audio mix from the battery, measure average power, then calculate runtime with the formula above. Retain a hardware current/brightness safety margin even if the firmware includes a power estimate.
